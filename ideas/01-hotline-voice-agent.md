## Problem Statement

AI agents are getting wallets. Every agent-payments demo shows the agent spending. Almost none show the human being asked first, in a way that reaches them wherever they are. Screens need an app open. Push notifications get swiped. A phone call interrupts.

Hotline is an onchain agent on Arc testnet you reach by dialing a phone number. You talk, it acts within limits you set. When something happens onchain that crosses a limit, it calls *you*, explains, and waits for a spoken yes. The phone call is the guardrail.

Target: UBC 2026 Hackathon, Agentic Payments & AI track, Best use of Arc, ElevenLabs + QuickNode bounties.

## What Makes This Cool

- **The phone rings on stage.** Mid-demo, a testnet USDC transfer lands in the agent's wallet. The presenter's phone rings. The agent explains what arrived and asks permission to act. The room hears the whole thing.
- **Guardrails you can hear.** "That's above your 50 USDC limit, say yes and your PIN to confirm." Policy tiers aren't a config page, they're dialogue.
- **No app.** Any phone. Zero install.
- **The agent pays its own way (stretch).** It buys a price quote from a 402-gated API for a fraction of a USDC, and the ledger shows the micropayment next to the human-approved transfers.

## Premises (agreed)

1. The phone call is the guardrail. All prior voice-crypto projects found (Cymatic, Call DeFAI Engine, Baseline, VoiceVault, several ETHGlobal entries) are inbound-only. Outbound approval calls are the differentiator and map to the track's "human approval for large transactions."
2. Arc **testnet**, faucet USDC, zero real funds. Our policy engine is the enforcement layer.
3. Solo TypeScript, zero custom contracts, **one wallet layer** (decided by a pre-hack spike, see Open Q1).
4. Trigger pipeline: onchain deposit → webhook or RPC watcher → decision loop → ElevenLabs outbound call. QuickNode Streams is the primary trigger for the bounty; an RPC event poller is the fallback that keeps the phone ringing.
5. Core scope is deliberately small: inbound (balance, send, pause), outbound approval on deposit, policy tiers, ledger, dashboard. x402 and swap/bridge are stretch, in that order.

Effort L. Risk Med. Mitigated by the cut lines and by A being a complete submission on its own.

## Recommended Approach

### Architecture

```
  Owner phone <── Twilio (number imported into ElevenLabs, native integration, both directions) ──> ElevenLabs Agent
       ^                                                                                              │ server tools
       │ POST /v1/convai/twilio/outbound-call (from backend)                                          │ HTTPS, header X-Hotline-Secret
       │                                                                                              v
       └──────────────────────────────────────────────────────────────────────────────────────  Backend (Node 22 / TypeScript / Hono)
                                                                                                   ├── Policy engine → AUTO | CALL | BLOCK
                                                                                                   ├── Ledger (SQLite on a persistent volume)
                                                                                                   ├── Wallet layer (ONE of: Circle Dev-Controlled Wallets on ARC-TESTNET, or viem + env key)
                                                                                                   ├── Chain reads via viem (Arc testnet RPC from QuickNode)
                                                                                                   ├── Deposit trigger: QuickNode Streams webhook (primary) or viem watchContractEvent poller (fallback)
                                                                                                   ├── Outbound call queue (one call at a time per owner)
                                                                                                   ├── GET /api/* → Dashboard (single page, 2 s poll)
                                                                                                   └── x402-shaped client + gated /quote endpoint (stretch 1)
```

**Identity and auth**
- Owner phone numbers live in config (`OWNER_NUMBERS`). ElevenLabs passes `system__caller_id` as a server-tool parameter (must be configured explicitly in each tool definition; it is not automatic). Backend rejects any tool call whose caller is not an owner, and the agent says it can't help.
- A 4-digit spoken PIN (`OWNER_PIN`, config) is required before any CALL-tier confirmation. Rules cannot be changed by voice at all.
- Known limitation, stated in README: caller ID can be spoofed; PIN mitigates, does not eliminate. Production would use Twilio Verify or a callback.
- Every ledger row stores `caller_id` and the ElevenLabs `conversation_id`.
- Server tools authenticate with `X-Hotline-Secret`, a per-deploy env var. Deposit webhook verifies QuickNode's HMAC security token.

**ElevenLabs server tools** (agent calls these mid-conversation; each must return within ~15 s, so nothing waits on chain receipts):
- `get_status()` → USDC balance, gas reserve, paused flag, last 3 ledger rows, and `pending_actions[]` (any CALL-tier actions awaiting confirmation). The agent calls this at the start of every inbound call so queued approvals get surfaced without the backend needing to push into a live call.
- `propose_action(kind, to_label, amount_usdc)` → runs policy engine. Returns `{action_code, decision, reason, summary, status}`. AUTO: submits the tx and returns `status: submitted` immediately; agent says "sending now." CALL: returns "needs confirmation." BLOCK: returns the rule name.
- `confirm_action(approved: bool, pin: string)` → acts on the single pending action bound to this `conversation_id` (server-side map, so the LLM never has to repeat an ID). Idempotent: a second call returns the original result without re-executing; a mismatched `approved` returns an error. Wrong PIN → one retry, then cancel with reason `bad_pin`.
- `get_action_status()` → status of the most recent action on this conversation: `submitted | confirmed | failed(reason)`, plus first 6 hex chars of the tx hash. Agent speaks "done, hash starts 0x3f2a… full link is on the dashboard."
- `get_rules()` → reads caps, allowlist labels, threshold, standing rules. Read-only by voice.
- `pause()` → sets `paused=true`. **Unpause is dashboard/config only.**

**Action codes:** short 6-char codes (e.g. `H-7K2Q`) in the ledger and dashboard. Voice never needs them because confirmation is bound to the conversation.

**Policy engine** (`decide(action) → AUTO | CALL | BLOCK`, evaluated in order):
1. `paused` → BLOCK `paused`
2. recipient not in allowlist → BLOCK `not_allowlisted` (allowlist is label → address, config/dashboard only)
3. `amount > PER_TX_CAP` → BLOCK `per_tx_cap`
4. `spent_today + amount > DAILY_CAP` (resets at `DAILY_RESET_UTC`, default 00:00 UTC) → BLOCK `daily_cap`
5. `balance - amount < GAS_RESERVE_USDC` → BLOCK `gas_reserve` (USDC is gas on Arc; never strand the wallet)
6. `amount > APPROVAL_THRESHOLD` or `source == stream` → CALL
7. else → AUTO

"Amount" is the USDC leaving the wallet. For `pay_api` it is the payment amount and it does accrue to the daily cap. Swap/bridge, if built, use the USDC input amount.

**Ledger row:** `code, ts, source (voice|stream|agent), caller_id, conversation_id, kind, to_label, to_addr, amount, decision, rule, status (auto|pending|confirmed|cancelled|expired|expired_no_answer|submitted|complete|failed), error, tx_hash, log_index, transcript_snippet, created_by_rule`.
Unique constraint on `(tx_hash, log_index)` for deposit-sourced rows. Dashboard links the stored transcript (fetched from the ElevenLabs conversations API after the call), not the ElevenLabs console.

**Confirmation semantics** (written into the agent's system prompt and tested):
- Only an unambiguous affirmative plus a PIN calls `confirm_action(true, pin)`.
- "Maybe", "wait", a question → agent answers or re-asks, max 2 re-asks, then `confirm_action(false)` with reason `unclear`.
- A counter-proposal ("send 80 instead") → `propose_action` with the new amount; the old pending action is cancelled server-side with reason `superseded`.
- The spoken "yes" snippet is stored in `transcript_snippet`.

**Standing rules** (config file and dashboard only; never voice):
```
standing_rules:
  - name: sweep_to_savings
    trigger: deposit
    condition: balance_after > 100
    action: { kind: send, to_label: savings, amount: balance_after - 100 - GAS_RESERVE_USDC }
```
A deposit that matches no rule writes an `observed` ledger row and does **not** call. A matching rule creates a CALL-tier action (rule 6 above).

**Deposit trigger and outbound flow (the climax):**
1. Primary: QuickNode Stream, Arc testnet, `logs` dataset, filter `address == USDC_TESTNET && topic0 == keccak(Transfer(address,address,uint256)) && topic2 == pad32(agent_wallet)`. Destination: webhook. Fallback: viem `watchContractEvent` on the same filter via RPC, ~20 lines, built **first** on Mon so the ring never depends on Streams latency.
2. Webhook handler: verify HMAC → iterate every log in the batch → `INSERT OR IGNORE` on `(tx_hash, log_index)` → only newly inserted rows proceed. At-least-once delivery is therefore safe.
3. Evaluate standing rules → create action → policy engine → CALL.
4. Outbound call queue: one active call per owner. If an inbound call is live, hold; the action is surfaced via `pending_actions[]` on the next tool call, and if the call ends without a decision, dial out. Multiple pending CALL actions coalesce into one outbound call that walks through them.
5. Outbound call via ElevenLabs with `conversation_initiation_client_data.dynamic_variables = {action_code, summary, amount, to_label, rule_name, balance}`; the system prompt references these.
6. Twilio answering-machine detection on; if machine or no answer: retry once after 90 s; then `expired_no_answer`. Any CALL action not confirmed within 10 minutes → `expired`. Expired actions stay visible on the dashboard with a "call in to re-propose" note.
7. Execution: submit, return immediately, poll receipt in the background (Circle's SDK is async: submit then poll for `COMPLETE`; viem is similar with `waitForTransactionReceipt`). On revert/timeout/insufficient balance → `failed` with the error; if still on the call, the agent says "that didn't go through, it's on the dashboard, nothing was sent."

**Dashboard:** one page, 2 s poll. Balance, rules, standing rules, ledger table with status and explorer links, stored transcripts, unpause button, "simulate deposit" button (dev only, disclosed in README if it is ever used in the demo). No auth beyond an unguessable path.

**x402-shaped stretch (honest scope):** backend hosts `GET /quote?pair=ETH-USD` that returns 402 with `{amount, pay_to}`; the agent's `get_quote` tool pays by a plain USDC transfer on Arc testnet and retries with `X-Payment-Tx` header; server verifies the tx on chain. Whether Arc testnet USDC supports EIP-3009 `transferWithAuthorization` (what spec x402 "exact" needs) is unverified, so this is labelled "x402-shaped, not spec-compliant" in the README unless the spike proves otherwise. Ledger row `kind: pay_api, source: agent`.
